## Decisions Made

- **`current_person` / `current_org` return dicts, not Pydantic models.** Until TASK-012 (Person model) and TASK-009 (Organization model) ship API schemas, a dict-based contract is the most decoupled — routers depend only on the documented keys. TASK-014/015 will likely upgrade these to typed dataclasses, but only after the real Person/Organization APIs exist; that's a router-side change, not a contract break.
- **`call_service_with_audit` does not commit.** The `get_db` dependency commits on successful return and rolls back on exception. Centralising the commit there means an HTTP-layer failure (e.g. response serialization) still triggers a rollback — if the helper committed itself, that path would silently persist the change. The helper rolls back explicitly on its own exception path so the session is clean before re-raising.
- **`resource_id_getter` and `next_state_getter` are callables, not eager values.** The audit row needs the resource ID after the operation has run (e.g. an autogenerated UUID flushed during `_write`). A callable defers extraction to post-operation; for callers without an autogen scenario, `lambda x: x.id` is the one-liner.
- **Test for the disabled-flag path uses `monkeypatch.setattr(settings, "auth_stub_enabled", False)` and constructs an `AuthContext` directly.** Calling `get_auth_context()` with the flag off raises 501 (TASK-014's job to replace), so the permission check is exercised by passing a manually-built `AuthContext` to the inner closure. This pins the rejection contract without depending on auth wiring that doesn't exist yet.
- **Audit-atomicity end-to-end already covered.** The existing `tests/test_compliance/test_audit_log.py::test_audit_failure_rolls_back_business_operation` exercises the same rollback semantics at the integration level. The new `test_dependencies.py` tests verify the **helper's contract** (propagate, don't swallow); the integration test verifies the **session-level outcome**. Together they cover both layers without duplication.
